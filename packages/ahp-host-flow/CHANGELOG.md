# Changelog

## [Unreleased]

### Security

- `.py` workflows are arbitrary code on the host, so they load by default only from the host and user sources: `[workflows] python_sources` in flow.toml (default `["user", "host"]`) must include `"workspace"` for a project's `.claude/workflows/*.py`, and client-published plugins never supply one.
- Credential masking before publishing (plan §4.9): a secret printed or returned by an inner agent is masked in the worker chat's text, reasoning, tool calls and results, structured calls (the `StructuredOutput` input and accepted result), approval and input prompts (`ToolConfirmation`, `InputRequest`), step results, `log()` lines, run errors, the `agent()` return and the journal (`[redact]` in `flow.toml`). Values under secret-named keys (`password`, `token`, `api_key`...) are masked at any depth. The inner agent's own view (prompts sent, replies, tool results and answers returned to it) is untouched. Known gaps: terminals, canvases and background work opened through `ScopedPublisher`, a secret split across a tool-call boundary mid-stream, and the best-effort builtin list (no `key=value` values under 8 characters, URL userinfo or `sk-` keys); the first two wait for the after-publishing layer (§4.9, M9).
- `ScopedPublisher` contains an inner session: a `chat=` it passes is honoured only for its worker chat or a tool chat it opened itself. A foreign chat (the run's main chat, another worker) is never reached: config changes, external turns and changesets naming one are dropped, and canvases, terminals, background work and tool chats are redirected to the worker chat. `dropped` is a bounded deque (`dropped_counts` keeps totals by kind), so progress spam cannot grow it.

### Fixed

- A config overlay that reaches a worker chat before its inner session is registered is applied once it is, instead of waiting for the next overlay.
- Customizations are re-published when a workflow source directory changes between runs (re-scanned at each run start and on describe; no file watching).
- Workflow discovery skips symlinks and non-regular files.
- A `CancelledError` raised by a `.py` workflow's own code (it awaited a task it had cancelled) no longer hangs the run or cancels the parent: it is a script error, "the script was cancelled", for the run and for an in-process child. Cancelling the run itself (the host killing it) still cancels it.
- The Python runner maps `Infinity`, `-Infinity` and `NaN` to `null` wherever a value crosses to the host (the return value, `agent()` opts, `workflow()` args, a child's value), as `JSON.stringify` does, instead of failing the run (`return {'left': budget.remaining()}` with no budget set); `log()` and `phase()` print them as JavaScript does.
- The Python runner's `parallel()`/`pipeline()` argument errors read "needs an array of ..." like the JS runner, as the docs claim.
- `Sandbox.run` checks the script's language before opening the journal, so a refused run leaves no journal behind.
- `agent()` no longer hangs when the host cancels the worker turn before it starts: the call returns `null` (skipped) and its inner session is cancelled and closed.
- A failure opening the worker chat, creating the inner session or running the turn now completes the main chat's `agent` tool call as failed instead of leaving it `running`.
- `flow run --config` fails at the first confirmation or input an inner session asks for, naming the call and suggesting `approval_mode`, instead of hanging; it is never auto-approved.
- Inner providers are now really loaded on first use. A provider that fails to load fails only the calls routed to it (`null` plus a log line) and is left out of the model list, instead of stopping startup.
- `flow run --config` rejects `--budget 0` and `--timeout 0` like any other engine flag.
- `python -m ahp_host_flow` refuses a non-loopback `--bind` without `--token-file`.

### Changed

- `agent()` ordinals and the current phase are assigned by the host (`Scheduler.issue`) when the request line arrives, not in the sandbox, so every runner of a run shares one counter and one phase; `phase()` only notifies. The `agent` request no longer carries `ordinal`, and its `phase` is the call's own override or null. A refused call (cap or budget) takes no ordinal.
- The Python runner needs `ahp-host-flow` installed in its interpreter (it runs with `python -I`, which ignores `PYTHONPATH`); an editable install counts.
- `import ahp_host_flow` and `import ahp_host_flow.sandbox` are lazy (PEP 562): the public names load on first use, so the Python runner starts without importing `ahp_host` or third-party packages.

### Added

- Fleet dispatch (plan §2, §8 M7) with thin worker chats: a provider with `via = "fleet"` runs each `agent()` call as a session on a gateway node through the gateway's fleet tools (`start_session`, `wait_for_sessions`, `read_session`, `stop_session`), called from the run's main turn with no model in between. The worker chat shows the status, a link to the node session, the result and its usage; the node session URI is the journal start record's dispatch handle. The call passes `opts.model` through `models`, else the run's own model when the provider's `models` names it or is empty. Skip and abort stop the node session; the host stopping does not (`FleetDispatcher(aborted=)`), so a resumed run can reattach. `RoutingDispatcher` picks the dispatcher by provider kind; `StepDispatcher` is the shared base. A call fails clearly when no gateway offers the tools, and a continued run waits for the gateway to rejoin (`FlowProvider(fleet_client_wait=...)`).
- Fleet tool calls are watched: when the gateway that offered the tools leaves, or no answer comes within `reply_timeout` (flow.toml, default 900 s; a `wait_for_sessions` slice adds 60 s), the call is retried once on the rejoined gateway (within `fleet_client_wait`), else it fails, `agent()` returns `null` and a log line says why. `start_session` is never retried.
- A fleet call whose approval mode the gateway refuses fails with a log line naming the mode, the provider and the setting to change (`approval_mode` in flow.toml, the run's Approvals, or the gateway's `child_config`), instead of the bare tool error.
- A continued run reattaches a fleet call cut off by a restart to its still-running node session (`wait_for_sessions`/`read_session` on the recorded session) instead of dispatching it again, unless the session is gone, in which case it is started anew with a log line (plan §4.8). This rides `resume_turn`: after a drain-restart by itself, after a crash on a client's `chat/turnResume`.
- Remote providers (plan §8 M7): `[providers.<name>] url`, `token_file`, `agent`, `idle_timeout` dials another host with ahp-client (`ClientDispatcher` in the engine, `RemoteWorkerChats` for the thin worker chat that shows the remote session and the remote turn's text once it completes, recorded as the journal start record's dispatch handle). A remote turn that goes quiet for `idle_timeout` seconds (default 600; an approval or question there cannot be answered from the run) is stopped and the call fails. A remote call cut off by a restart is not reattached: the remote turn it left is stopped, with a log line, and the call runs again. `FlowProvider(remote_dialer=...)` lets tests dial an in-memory host.
- The resume log line for a cut-off call that recorded a session no longer claims every one is reattached: it names the session and leaves the outcome to the dispatcher, which logs what it did (reattached, gone and dispatched again, or a remote turn stopped).
- The `flow` agent type for ahp-node (`[[agents]] type = "flow"; config = ".../flow.toml"`), registered in the `ahp_host.agents` entry points; runs persist in the node's state directory unless flow.toml sets `state_dir`.
- Fleet and remote providers in flow.toml: `[providers.<name>] via = "fleet"; node; agent` (a call runs on a gateway node) and `url; token_file; agent` (dial another host directly), with `reply_timeout` (fleet) and `idle_timeout` (remote) in seconds; `ProviderConfig.kind`, and `LazyProviders` lists only in-process providers.
- Start records carry the node session (`DispatchHandle.session`, `StartRecord.session`); a continued run hands dispatchers the handle a cut-off call recorded (`reattach_handle()`), so a fleet or remote dispatcher can reattach instead of re-dispatching.
- Tests: a real in-memory gateway (`tests/fleet_hosting.py`; `ahp-gateway` is a test-only `dev` dependency, kept out of `src` by an import-linter contract) covers fleet runs, structured results, `max_running`, skip, abort, a refused approval mode, the run's model, a flow-host drain-restart and crash (reattached, through the real gateway, without touching the store or the links), a mid-call gateway restart (retried) and a gateway restart between runs; fake-gateway tests cover reattach, liveness and the reply deadline; remote tests cover the idle timeout and the cut-off remote turn.
