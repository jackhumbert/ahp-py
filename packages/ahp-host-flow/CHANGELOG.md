# Changelog

## [Unreleased]

### Added — the resume-key hook (M12)

- `RunOptions.key_extra` (a callable taking an `AgentCall`) and `key_mode` (its name in the journal): the hook's JSON value joins each `agent()` call's key as an `extra` field, so a cached call replays only for the same value. With no hook every key is byte-identical to before (`call_key(call, extra=...)`; an extra of `None` still adds `"extra": null`). `key_mode_name()` is `default`, the given `key_mode`, or the hook's `module:qualname`; the options reject a mode without a hook and `default` with one.
- The key is taken at issue time, before dispatch and before the ordinal, so a hook that raises or returns non-JSON makes that `agent()` throw `resume key hook failed for agent() #<n>: ...` and takes no ordinal. `Scheduler.admit(call, key=None)`, `Replay.lookup` and `Replay.reattach` take the key.
- The journal header records `options.keyMode` (`RunHeader.key_mode`; a journal without it reads as `default`). A resume whose mode differs from the old run's logs one line and replays no `agent()` call (gate and verb replays still apply).
- `library.run(key_extra=fn)` sets the hook; `FlowRun.agent` turns a failing hook into a failed future.
- `flow.toml` gains `[resume] key` (`ResumeConfig`): `"default"` (the old keys), `"model"` (each call's key gains `{provider, model}`) or `'module:function'` (called with the `AgentCall` and that route; its value is the extra). A bad value is a config error.
- `routing.resolved_route(config, call, run_model)` is the route from the config alone, known before dispatch: the pinned or routed provider, and the model as `opts.model` (a `models` alias expands, an unknown one passes through), else the run's model when the provider lists it, else None. `loading.resume_key_hook` builds the hook and its journal mode; `FlowProvider` sets it on each run, and a continued run uses the model of the run it continues. A path that cannot be imported fails the turn (`resume.key: cannot import ...`).
- README sections `Custom verbs` and `Resume keys`, the expanded `Custom verbs` and new `[resume] keys` parts of `docs/format.md`, plan status and M12 result, and the AGENTS.md invariants.

### Added — custom verbs in the sandbox (M12)

- A new `verb` request {name, args} -> {value} on the wire, with `VERB_ERROR` (-32008) for a failed handler; `run` takes `verbs?: [str]`, and both runners define one global per name after the built-ins (so `ask`, `approve` and `canvas` may be replaced), children included. The host takes the verb ordinal when the line arrives and re-checks the name: an undeclared name or a malformed request gets `INVALID_PARAMS`.
- `Sandbox.run` and `run_script` take `verb_host=`; `RunState` carries a `VerbRunner`, which the library API builds too. Python workflows also get `ahp_host_flow.verbs.verb(name, *args)`; `ask()`, `approve()` and `canvas()` from that module say so when the run replaced them.
- Conformance script `extensions/verbs` (JavaScript and Python twins) and a `Custom verbs` section in `docs/format.md`.

### Added — custom verb runner (M12)

- `engine.VerbRunner` runs a run's custom verbs: its own ordinal counter, call ids stable across a resume, an `open`/`done`/`error` journal record per call, masked arguments, results and errors, abort that cancels a running handler (leaving only the `open` record, so a resume calls it again), and replay of finished calls without calling the handler. Verbs take no agent cap, budget or concurrency slot. A handler gets a `VerbCall` with a `VerbContext` (`ask` and `confirm` raise `GateUnavailableError` when no client can answer); a `VerbHost` supplies the context and shows progress.
- `RunOptions.verbs` maps verb names to handlers. Names match `[A-Za-z][A-Za-z0-9_]*` and may not be one of `RESERVED_VERBS`, a JavaScript or Python reserved word, a JavaScript standard global (`Object`, `JSON`, `console`, ...), a name the sandbox keeps absent (`require`, `process`, `fetch`, ...) or a Python builtin; `ask`, `approve` and `canvas` (`REPLACEABLE_VERBS`) may be replaced. `verb_name_error` explains a refusal.

### Added — custom verbs (M12)

- The journal gains `verb` records (`VerbRecord`: ordinal, key, name, call id, `open`/`done`/`error`, masked value or error); a finished record wins over an open one on load, `LoadedJournal.verbs` and `open_verbs` expose them, and `JOURNAL_VERSION` stays 1. `verb_key` (sha256 of the canonical JSON of name and args) and `verb_call_id` (`verb-<key[:16]>-<occurrence>`, stable across a resume) name a call.
- `VerbReplay` serves finished verb records by call id and key, once each, in a prefix resume and with `continue_run` alike, and never touches the `agent()` replay; `JournalRun.verb_replay` is set whenever a run resumes.

- `run(verbs={name: handler})` and `FlowRun.verb(name, *args)` call custom verbs from the library API with no model; a bad name is a `ValueError` (reserved or unknown), a handler error a `VerbFailedError`, and with no host a handler's `ask`/`confirm` fail like gates do.
- `FlowProvider` runs `[verbs]` handlers on a hosted run: `MainChatVerbs` shows each call as a tool call on the main chat (`verb-<ordinal>`, `verb-r<k>-<ordinal>` in a continued run) with `verbStarted`/`verbFinished` descriptors, masked arguments and results, and verbs replayed from the journal are not published again. A replaced `approve()` raises no confirmation.
- `flow.toml` gains a `[verbs]` table (`name = "module:function"`). A reserved or malformed name is a config error; `loading.lazy_verbs` builds a `LazyVerb` per entry, which imports its handler on the first call only and caches a failed import (`import_object` is shared with provider loading, whose messages are unchanged).
- A hosted verb's `context.ask(question, options)` is an input request on the main chat and `context.confirm(summary, options)` a tool confirmation (`approve`), both through a `MainChatGates` of their own (ids `verb-<ordinal>-<k>` and `verb-<ordinal>-<k>-<attempt>`, distinct from the verb's call and from `gate-...`); prompts are masked, the answer reaches the handler as typed, `ask` gives None when declined, bad options raise `ValueError` as for `ask()`/`approve()`. They are not journaled: a handler finds a request it already made by `call.call_id`, which is stable across a resume.
- Verbs replay and re-call across a restart (a `FileSessionStore` drain or crash, resumed by itself or by `chat/turnResume`): a finished verb is served from the journal without calling its handler, a cut-off one is called again with the same call id and a `resume: <name>() #<n> was cut off...` notification, and the continued run's calls are `verb-r<k>-<ordinal>` with the cut-off `verb-<ordinal>` cancelled. `test_customverb_restart` covers it in JS and Python; no source change was needed.
- README sections `Custom verbs` and `Resume keys`, the expanded `Custom verbs` and new `[resume] keys` parts of `docs/format.md`, plan status and M12 result, and the AGENTS.md invariants.

### Added — delegation origin on fleet calls (M11)

- A fleet call's node session is created with a delegation `origin` (`{kind: "ahp-py/delegation", session, chat, toolCallId}`) naming the run session, the call's worker chat and its `agent` tool call, sent as `start_session`'s `originChat` and `originToolCall`; node listings carry it, so a client can nest the session under its call.

### Added — `workflow()` reaches client workflows and source-qualified names (M11)

- `workflow('host:child')` (also `client:`, `workspace:`, `user:`) reaches one source only; an unknown source throws `unknown workflow source 'x' in 'x:child': use one of client, workspace, user, host`. A bare name tries client, workspace, user, host in that order, as for a top-level run.
- The engine takes client workflows as data: `RunOptions.client_workflows` (`ClientWorkflow`, `.js` only) and labeled `WorkflowDir` entries in `workflow_dirs`; `Registry` gained `client=`, `find_client` and `_split`. `config.SOURCES` is now `engine.WORKFLOW_SOURCES`.

### Added — kept worktree changesets survive a restart (M11)

- A kept worktree is stored in the session's resume state and republished as a new changeset (Apply and Discard working) after a host restart; one whose directory is gone is dropped with a log line. `FlowProvider` implements ahp-host's `ResumesOnRestore` for sessions holding kept worktrees.
- `python -m ahp_host_flow` now stores sessions under `state_dir` and calls `host.restore()` before serving; `--no-store` keeps the old in-memory behaviour. `build_host` takes `store=`.

### Changed — worktree operations declared by the provider (M11)

- `FlowProvider` implements ahp-host's `ProvidesOperations` (`changeset_operations`) and declares Apply and Discard itself, so a kept worktree's changeset is actionable under ahp-node as well as in `python -m ahp_host_flow`, `flow run` and any embedder's `Host`. The operation ids are unchanged.

### Removed — `register_worktree_operations` (M11)

- `ahp_host_flow.worktree.register_worktree_operations` is gone; nothing needs to register the operations on a host any more.

### Added — watched workflow dirs (M11)

- A flow session watches its local workflow dirs (workspace `.claude/workflows`, user, host) and re-publishes the customizations when a `*.js` or `*.py` is added, edited or deleted, with no message sent. `[workflows] watch_interval` in flow.toml sets the scan interval in seconds (default `2.0`; `0` turns watching off). A watch-triggered refresh never reads a client.

### Added — subagent preamble (M11)

- A line of context goes before the prompt an in-process, fleet or remote provider's inner agent is sent (`engine/preamble.py`: `DEFAULT_PREAMBLE`, `preamble_text`, `with_preamble`). It is on by default; `preamble = false` in a provider's flow.toml table sends the bare prompt, and a string replaces the text. The default text tells the agent its final message is the step's return value. Worker chats, the main chat's `agent` tool call and journal keys keep the bare prompt. In a named chat (`opts.x.chat`) only the first message carries it, since the inner session already has it. The test fakes strip it through `tests/preamble.py`.

### Added — `from_config` loading (M11)

- The loader gives an inner provider's factory `roots` and `state_dir` when it has a parameter of that name (not a bare `**kwargs`) and the table does not set it: the host's roots plus `<state_dir>/runs` (named `flow-runs`, `flow-runs-2`, ... among named roots), and `<state_dir>/providers/<name>`. `FlowProvider(roots=)`, the `flow` node agent (`node.roots`), `flow run --config` (the working folder) and `python -m ahp_host_flow --root PATH` (repeatable) supply the host's roots.
- `[claude]` and `[acp]` extras install `ahp-host-claude` and `ahp-host-acp`, so a flow.toml can name `ahp_host_claude:from_config` and `ahp_host_acp:from_config` directly. README and plan §5 use them instead of wrapper factories.

### Added — extensions (M10)

- `ask()`, `approve()` and `canvas()` verbs in both the JS and the Python runner, with identical argument errors. They reach the host as a `gate` request (`{kind, question, options}` -> `{value}`) and a `canvas` notification (`{url, title}`); `protocol.GATE_ERROR` (-32007) is the error for a gate no client can answer, whose message the verb throws. Gates take their ordinal from a counter separate from `agent()` ordinals, assigned when the request line arrives and shared with `workflow()` children. The engine (`GateRunner`, `engine/gates.py`) re-validates an `ask()` answer against `choices`/`schema`, masks it once, and returns `null`/`false` for a gate aborted mid-wait. Without a `Gates` implementation `ask()`/`approve()` fail clearly and `canvas()` is ignored with a log line.
- Gate journal records: every `ask()`/`approve()` writes a `type: gate` line (ordinal from the gate counter, key = sha256 of kind, question and options, status `open` or `answered`, masked answer) before asking and after the answer. On resume (prefix or `continue_run`) an answered gate whose question and options are unchanged replays its answer by key without asking, and a gate still open is asked again (logged); gates never end the `agent()` cache. `JOURNAL_VERSION` stays 1 and older readers ignore the new record type.
- Gates on the run's main chat (`gates.py`, `MainChatGates`): `ask()` is an input request with a select, text, number or boolean form built from `choices` or a flat `schema` (any other schema is a JSON text answer), asked up to 3 times in all on an invalid answer (`ASK_ATTEMPTS`), then `null` with a log line; `approve()` is a tool confirmation with an edits preview of its `diff`; `canvas()` goes through `canvas_set` (experimental in AHP 1.0.0) and stays on the main chat after the run. Prompts and answers are masked, a schema property's title shown with a question is masked like the rest of it (option ids stay as typed, since answers must match them), an open request is withdrawn when the run is aborted (on a client's cancel the host's own turn cancellation already clears `inputNeeded` and cancels the approve call, so the gates' withdrawal frames are dropped as no-ops there; `test_flowext_gateform_abort_withdraws_*` prove the gates send them), and `flow run --config` fails clearly at a gate ("the workflow's ask() gate needs an answer") because no client is connected. The Python twins of the host gate tests run without Node.
- An open gate cut off by a host restart is withdrawn with a notice and asked again on the resumed turn (as a new request, its tool call under a `gate-r<k>-` id); answered gates replay from the journal without asking.
- `opts.x.provider` pins one `agent()` call to a configured provider (wins over routing rules and the default; a non-object `x` or a non-string/empty provider is ignored); an unknown name fails that call (`null` plus a log line naming the configured providers).
- `opts.x.chat` names a worker chat whose inner session is reused across calls (follow-up turns in one chat; calls to one name are serialized; the chat keeps its first call's config, so a follow-up asking for another `effort` or approval mode runs with the first and logs a line saying so, while `model` goes with each message; closed when the run ends; in-process providers only, refused for fleet/remote and with `isolation: 'worktree'`; on resume the chat and session are recreated and the inner agent forgets earlier turns unless its provider resumes sessions).
- `opts.x.attach` hands an `agent()` call files and prior results as message attachments: `{kind: 'file', path, label?}` becomes a resource attachment (`uri`, `label`, guessed `contentType`) and `{kind: 'result', value, label?}` an embedded JSON resource; the prompt text is unchanged (nothing inlined). In-process providers only; a bad entry fails the call (`null` plus a log line).
- `meta.x.schedule` (a cron string or `{expression, timeZone}`, `UTC` by default) is offered as `_meta['ahp-py/flow'].schedule` on the workflow's customization; an invalid one (checked as ahp-host checks a saved definition) is left out, listed with `warnings` and logged, and the workflow is still listed. A client applies it with `ahp_protocol.ext.flow.with_offered_schedule`; the host never creates the automation itself.
- `shim/flow-shim.js` (paste after meta; keeps the real gates under ahp-host-flow, falls back to agent() or FLOW_SHIM defaults under Claude Code) and the dual-target conformance script `conformance/shim/dual_target.js`, checked under a minimal Claude-Code-like harness and through the provider; Python workflows are ahp-py-only, so there is no Python shim.
- The shim ships with the package as `ahp_host_flow/shim/flow-shim.js` (`ahp_host_flow.shim.source()`, and `flow shim` prints it), byte-identical to the repository's `shim/flow-shim.js`.
- Docs: `docs/format.md` has an Extensions (ahp-py only) section, the README an Extensions section, `AGENTS.md` the M10 invariants, and `docs/plan.md` §6 as built, the status line, the M10 result and the list of what is open after M10.

### Security

- Gate options are re-checked by the host (`engine/gates.options_error`, in `GateRunner.issue`): a script could make the JS runner send options its own checks never saw (a `toJSON` on `choices` or `diff`, a replaced `JSON.stringify`), and the host passed them to the main chat's form unchecked. Unknown keys, malformed `choices`/`schema`/`diff`, and `choices` with `schema` are now refused before a gate ordinal is taken; the verb throws the host's reason. An adversarial audit of the gate verbs (`test_flowext_sandbox_escape`) found no realm escape: their values, promises, errors and prototype chains stay in the script realm, answers cross as JSON only, and a JS child's verbs are its own.
- Attached file paths (`opts.x.attach`) are resolved (symlinks followed) and must be regular files inside the run's working directories; anything else fails the call before a worker chat opens.
- `[workflows] python_sources` can never include `client`: a client cannot supply a `.py` workflow, and the config is refused.
- A client-published workflow listing is trusted for names only as plain file names: an entry with a path separator or `..` (`../x.js`) is skipped, so the read URI never leaves the plugin's `workflows/`. The 1 MiB cap bounds what is kept, not what the client sends (the plugin read API returns the whole file).
- `.py` workflows are arbitrary code on the host, so they load by default only from the host and user sources: `[workflows] python_sources` in flow.toml (default `["user", "host"]`) must include `"workspace"` for a project's `.claude/workflows/*.py`, and client-published plugins never supply one.
- Credential masking before publishing (plan §4.9): a secret printed or returned by an inner agent is masked in the worker chat's text, reasoning, tool calls and results, structured calls (the `StructuredOutput` input and accepted result), approval and input prompts (`ToolConfirmation`, `InputRequest`), step results, `log()` lines, run errors, the `agent()` return and the journal (`[redact]` in `flow.toml`). Values under secret-named keys (`password`, `token`, `api_key`...) are masked at any depth. The inner agent's own view (prompts sent, replies, tool results and answers returned to it) is untouched. The run's own `canvas()` title and URL are masked before `canvas_set`. Known gaps: terminals and background work opened through `ScopedPublisher`, a secret split across a tool-call boundary mid-stream, and the best-effort builtin list (no `key=value` values under 8 characters, URL userinfo or `sk-` keys); the first wait for the after-publishing layer (§4.9, M9).
- `ScopedPublisher` contains an inner session: a `chat=` it passes is honoured only for its worker chat or a tool chat it opened itself. A foreign chat (the run's main chat, another worker) is never reached: config changes, external turns and changesets naming one are dropped, and canvases, terminals, background work and tool chats are redirected to the worker chat. `dropped` is a bounded deque (`dropped_counts` keeps totals by kind), so progress spam cannot grow it.

### Fixed

- A config overlay that reaches a worker chat before its inner session is registered is applied once it is, instead of waiting for the next overlay.
- Customizations are re-published when a workflow source directory changes between runs (re-scanned at each run start and on describe; no file watching).
- Workflow discovery skips symlinks and non-regular files.
- A `CancelledError` raised by a `.py` workflow's own code (it awaited a task it had cancelled) no longer hangs the run or cancels the parent: it is a script error, "the script was cancelled", for the run and for an in-process child. Cancelling the run itself (the host killing it) still cancels it.
- The Python runner maps `Infinity`, `-Infinity` and `NaN` to `null` wherever a value crosses to the host (the return value, `agent()` opts, `workflow()` args, a child's value), as `JSON.stringify` does, instead of failing the run (`return {'left': budget.remaining()}` with no budget set); `log()` and `phase()` print them as JavaScript does.
- The Python runner's `parallel()`/`pipeline()` argument errors read "needs an array of ..." like the JS runner, as the docs claim.
- `Sandbox.run` checks the script's language before opening the journal, so a refused run leaves no journal behind.
- `agent()` no longer hangs when the host cancels the worker turn before it starts: the call returns `null` (skipped) and its inner session is cancelled and closed.
- A failure opening the worker chat, creating the inner session or running the turn now completes the main chat's `agent` tool call as failed instead of leaving it `running`.
- `flow run --config` fails at the first confirmation or input an inner session asks for, naming the call and suggesting `approval_mode`, instead of hanging; it is never auto-approved.
- Inner providers are now really loaded on first use. A provider that fails to load fails only the calls routed to it (`null` plus a log line) and is left out of the model list, instead of stopping startup.
- `flow run --config` rejects `--budget 0` and `--timeout 0` like any other engine flag.
- `python -m ahp_host_flow` refuses a non-loopback `--bind` without `--token-file`.

### Changed

- `agent()` ordinals and the current phase are assigned by the host (`Scheduler.issue`) when the request line arrives, not in the sandbox, so every runner of a run shares one counter and one phase; `phase()` only notifies. The `agent` request no longer carries `ordinal`, and its `phase` is the call's own override or null. A refused call (cap or budget) takes no ordinal.
- The Python runner needs `ahp-host-flow` installed in its interpreter (it runs with `python -I`, which ignores `PYTHONPATH`); an editable install counts.
- `import ahp_host_flow` and `import ahp_host_flow.sandbox` are lazy (PEP 562): the public names load on first use, so the Python runner starts without importing `ahp_host` or third-party packages.

### Added — redaction after publishing (M9)

- Journal: `redact_agent_record(state_dir, run_id, ordinal, reason=, redacted_at=)` rewrites a finished `agent()` record in place (value and error become `[redacted]`, atomic replace, torn tail dropped). Agent records carry an optional `redacted` marker (`{reason, redactedAt}`); `JOURNAL_VERSION` stays 1 because older readers ignore the key. A run resumed from a redacted journal replays `[redacted]` and keeps the marker.
- `ahp_host_flow.redaction`: `find_step` (where a run's call is shown on this host), `redact_step` (journal first, then the worker chat's parts and the `agent` tool call through `Host.redact`; refuses a live run; lists resumed descendants), a request spool (`queue_request`, `process_requests`, `result_path`) and a poller (`start_poller`) for a running server. The prompt, the final value and the inner agent's own context are not redacted. `FlowProvider.live_run_ids()` names the runs live now.
- `flow redact <runId> <ordinal> [--reason]` with `--state-dir DIR` (journal only, no host; never on a run a `flow run` is still writing) or `--config flow.toml` (queues a request under `<state_dir>/redact` and waits `--wait` seconds, default 10, for the host's answer). Exit codes: 0 done, 1 refused or failed, 3 no running host picked the request up yet (it stays queued and is applied when a host next starts). `python -m ahp_host_flow` starts the request poller after the websocket server is up and cancels it on the way out; file-system access to the state dir is the authorization, as for journals.
- Review fixes: `redact_step` requires a stated `actor` (the request spool records `flow redact (local operator <user>)`, or the `actor` a request names), so the audit's "who" is never null. A journal's writer holds `journal.lock` while it is open and `redact_agent_record` raises `JournalBusyError` instead of rewriting under a live writer, in this process or another, which also guards `--state-dir` and the direct API (a journal from before the lock has none to find). A redaction that fails part way raises `RedactionError` listing what was already redacted (`.done`, also in the spool result and printed by `flow redact`); redacting again finishes it. README states plainly that the journal header's script source and `args`, `workflow` records and the main chat's message holding the script text are not redacted. The end-to-end test now checks the stored session of the worker and main chat and, after two restarts, a `chat/turnResume` of the cut-off run replaying `[redacted]`.
- Documented: README "Redacting after publishing", AGENTS, and plan §4.9, §8 (M9 result) and §10. **The agent's own context is not redacted**: the inner session's conversation and provider state keep the original; only the shared view and the journal change.

### Added

- Steering interactive worker chats (plan §4.5): with `interactive = true` a provider's worker chats open `full`, and a steering message on a running one is forwarded to the inner session if it takes steering mid-turn, else rejected with a reason; other worker chats stay read-only.
- Per-child changesets: a worktree an `agent()` call kept (`isolation: 'worktree'` with changes) is published as a changeset on its worker chat, with Apply (to the working tree) and Discard operations (`register_worktree_operations`, called by `flow serve` and `flow run`; an embedder registers them on its own host). The worktree stays until the changeset is resolved. Under ahp-node's `flow` agent, which cannot register operations, the changeset has none. Known gap: the changeset's files are the worktree's, verbatim and unmasked (masking would corrupt the diff).
- Worktree helpers for per-child changesets: `worktree_changes` (a kept worktree's file changes at the paths they land on), `worktree_patch`, `apply_to_repo` and `discard_worktree`.
- Automations run workflows unattended: a saved automation whose message is `/<workflow> <json args>` starts a fresh flow session through ahp-host's automation machinery (manual or cron) and its run is an ordinary flow run (journal, typed progress); a client workflow the template names is captured by the host at save time, so the run never reads the client. A workflow's own default schedule (`meta.x.schedule`) is offered on its customization for a client to apply (see the extensions above).
- `client` workflow source in `flow.toml` (`[workflows] sources`), the highest precedence (`client`, `workspace`, `user`, `host`) and off by default: the default is `["workspace", "user", "host"]`, so a shared host runs a client-published workflow only when the operator opts in.
- The acceptance corpus (plan §3): four real-world-shaped scripts under `conformance/corpus` (`build_to_spec`, `fanout`, `triage`, `commit_prep`), each run unmodified through the provider on a scripted fake (`tests/corpus_fakes.py`) with its structure asserted; `fanout.js` is rewritten with schemas, and its opt-in live test stays behind `AHP_FLOW_LIVE_CONFIG`.
- Client-published workflows in sessions (opt-in, `[workflows] sources` with `client`): listed beside the other sources, run by `/name` or `/client:name` from the text the client served (the journal snapshots it, so resume never needs the client), and re-published live when a client republishes its plugin (re-read in a task, never inline in the client's notification).
- Catalog reads client-published workflows (`workflows/*.js` in a plugin a client publishes) through a `PluginReader`, lists them first in their own `ahp-host-flow.client.<plugin>` container with `shadowedBy` markers, and never reads a client's `.py` (bounded to 200 files of 1 MiB per plugin).
- Docs for M8: README (the `client` source under "Where workflows come from", "Operations": automations, worktree changesets, steering), AGENTS.md (client `.py` never read, no client reads inside `active_clients_changed` or `describe`, the provider's own container for client workflows, worker chat interactivity, the operation ids, the corpus scripts) and `docs/plan.md` (status, §4.3-§4.5, the M8 result note); `docs/format.md` reserved `meta.x.schedule`, now documented under its Extensions section.
- A kept worktree whose changes are empty once read (a commit that leaves the tree as it was, a mode-only change) is kept, not removed, since it may hold a commit: the log line says "but no reviewable changes; remove with `git worktree remove --force <path>`", and no changeset is published.
